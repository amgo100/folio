# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

## Build, lint and test

Rust edition 2024, MSRV 1.95 (`rust-version` in `Cargo.toml`). There is no hosted CI: checks run locally. Before every push, run `scripts/check.sh` and push only if it ends with "all checks passed" (`--fast` skips the MSRV check and cargo-deny while iterating, not before a push). It runs:

```bash
cargo build --workspace --all-targets --locked
cargo test --workspace --all-features --locked
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo fmt --all --check
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --all-features --locked
cargo +1.95 check --workspace --all-targets --all-features --locked
cargo deny check                  # licences, advisories, bans, sources; config in deny.toml
cargo deny --manifest-path fuzz/Cargo.toml check   # the fuzz workspace, same config
```

- One test: `cargo test -p folio-component --test dependency_direction`. `cargo test -p folio --test toolchain` installs a fake release, signed with a key made for the test, and builds a project that pins it. `cargo test -p folio-testkit --test differential` checks incremental compiles against fresh ones (`FOLIO_DIFFERENTIAL_CASES=<n>` for more cases); `cargo test -p folio --test incremental` checks which queries and pages an edit reuses. Run the binary with `cargo run -- build --root tests/corpus/exam`; `cargo test -p folio --test cli` runs it on the corpus.
- One-time setup: `rustup toolchain install 1.95 --profile minimal` and `cargo install cargo-deny --locked`. For the benchmarks, Valgrind and `cargo install gungraun-runner --version <the gungraun version in Cargo.lock> --locked`; for fuzzing, `rustup toolchain install nightly --profile minimal` and `cargo install cargo-fuzz --locked`.
- `tests/README.md` describes the test layout and what runs when. `scripts/bless.sh` rewrites every golden file (layout dumps, shaped paragraphs, determinism digests) and prints what changed; review the diff before committing. `scripts/bench.sh` is the regression gate (instruction counts against the merge base, fails above 3%): run it before pushing a branch that may affect performance and after each merge to main. `scripts/bench.sh --wall` times the M0 exit check (200 ms) and the reference document: full compile, edits, the preview path (edit to pages, against the M1 exit check's 80 ms), a stylesheet edit, three variants against one, times per stage, and a typing session. `scripts/fuzz.sh [seconds]` is the fuzz smoke job; commit a failing input to `fuzz/regressions/<target>/` with its fix, where `cargo test -p folio-testkit --test fuzz` replays it on stable. None of the three is part of `scripts/check.sh`.
- `tests/office` holds the hand-written DOCX and PPTX fixtures that verified the Office assumptions of SPEC §16.2, with their generator (`generate.py`, standard-library Python), the Windows probes that measure them in Word and PowerPoint, and the results in its README. They are not part of `scripts/check.sh`.
- `tests/corpus` holds the test corpus, one project per directory; every build goes through the layout golden files (`cargo test -p folio-testkit --test golden`, `tests/golden/layout`), the PDF and determinism tests and the CLI test. For PDF, `cargo test -p folio --test pdf` checks it with krilla's PDF/UA-1 validator, and `python tests/pdf/corpus.py` (needs veraPDF and Poppler's `pdftotext`) checks it with veraPDF's PDF/UA-1 profile and that extracted text round-trips. The script is not part of `scripts/check.sh`; run it after changes to `folio-pdf` or to what layout draws.
- `tests/pdf` holds the krilla prototype (its own Cargo workspace and lockfile, so krilla stays out of the main workspace) that wrote the fixtures verifying the PDF assumptions of SPEC §16.2, the fixtures in `tests/pdf/out`, `validate.py` (runs veraPDF and checks the recorded results), and the results in its README. They are not part of `scripts/check.sh` either.
- Crates live in `crates/` (`folio-syntax`, `folio-component`, `folio-core`, `folio-fonts`, `folio-text`, `folio-pdf`, `folio`, and `folio-testkit` for the tests). `folio-core` holds the stages that are not yet their own crates; split crates out of it as interfaces settle (§2.2).
- Determinism (SPEC §2.4, §14.2): `cargo test -p folio --test determinism` builds the corpus in `tests/corpus` in two child processes that differ in strategy, threads, hash seeds, time zone, locale, `SOURCE_DATE_EPOCH` and working directory, compares the bytes, and compares the digests with `crates/folio/tests/determinism/digests.txt`, recorded on another machine. After a change meant to alter the output, run `FOLIO_BLESS=1 cargo test -p folio --test determinism` and commit the digests; a mismatch nobody intended is a determinism bug. `.gitattributes` keeps the corpus at LF line endings so that every checkout has the same input bytes.
- Golden files: `tests/golden/layout/*.txt` hold the pages of the corpus builds, `crates/folio-text/tests/golden/*.txt` shaped paragraphs. After a change meant to alter them, run `scripts/bless.sh` (or `FOLIO_BLESS=1` on one golden test) and review the diff before committing.
- Lints are set once in `[workspace.lints]` in the root `Cargo.toml`; every crate has `[lints] workspace = true` and `#![forbid(unsafe_code)]` in each crate root (`lib.rs`, `main.rs`), except `folio-fonts` (see Constraints). `missing_docs` is on, so public items need doc comments.
- **Dependency direction**: `folio-component` must not depend (normally or at build time) on any other workspace crate except those in `ALLOWED` in `crates/folio-component/tests/dependency_direction.rs` (`folio-text`, and `folio-draw` once it exists; their own dependencies are checked too, so `folio-text` depends on no other workspace crate). The test fails otherwise; move shared types into `folio-component` instead of widening the list.
- New dependencies must pass `deny.toml`: permissive licences only, no unknown registries or git sources.

## Code derived from Typst

`folio-syntax` (from `typst-syntax`) and `folio-math` (from Typst's math layout) derive from Apache-2.0 code. When importing Typst code: copy from a tagged release, keep Typst's copyright line, put the attribution header shown in `NOTICE` at the top of every derived file, update that crate's entry in `NOTICE`, and refresh `third_party/typst/LICENSE` and `NOTICE` if the release differs from the one recorded. Folio's own licence is undecided (SPEC §16.1).

## Pull requests

Every pull request is reviewed with the `/code-review` skill (which may spread the review over reviewer subagents, depending on effort level):

- Before opening a PR, and before every later push to one, run `/code-review` on the branch's diff against `main`. Fix confirmed findings, or say in the PR why one does not apply, before pushing.
- When asked to review or check someone else's PR, use `/code-review <PR number>` rather than reviewing by hand; add `--comment` only when asked to post the findings on GitHub.
- This applies to spec-only and documentation changes too.
- Every PR targets `main`. When work builds on an unmerged PR, cut the branch from that PR's branch but still open it against `main`, start its body with "Depends on #N — merge that first", and merge `main` in once #N lands. A PR based on another branch can be merged into that branch after it has landed, and one left with no commits of its own after its base merges is closed as merged with its `Closes` issue.
- The status paragraph of this file is one line that every branch would conflict on: in parallel work, propose its new wording in the PR body and apply such proposals together in one PR.

## Issues

- Every issue gets a GitHub issue type: `Bug` for behaviour that is wrong or contradicts the spec (test and benchmark tooling that gives wrong results included), `Feature` for functionality a user can use (a teacher, an agent, or a developer of the library), `Task` for everything else (groundwork, refactors, performance work, tests, docs, spec decisions). Add the matching `bug` or `enhancement` label and an `area: <name>` label as well.
- Milestones are `M<n> — <name>` (SPEC §15); a milestone's follow-up work is collected under an issue labelled `epic`, with the work as its sub-issues.
- Multi-issue runs with the project-manager skill read `.claude/pm-profile.md` (gate, hot spots, what goes to the user as a decision).

## Working on the specification

`docs/SPEC.md` is the single source of truth for the design. When editing it:

- Sections are cross-referenced by number (`§7.3`, `§10.5`) throughout, and the requirements table in §1.2 maps R1–R17 to sections. Renumbering or moving a section means updating every reference to it, including the §1.2 table, the roadmap (§15) and the assumptions table (§16.2).
- Terms in the §1.5 terminology table (element, component, variant, numbering group, common tree, flow state, live region, fragment, span map…) are used with those exact meanings; keep new text consistent with them, and add new terms there.
- Undecided points go in §16.1 (open questions) or §16.2 (assumptions with a verification method), not as hedges inside the normative sections.
- The spec uses British spelling (memoised, colour, licence, behaviour) and short declarative sentences.
- Diagrams are Mermaid blocks followed by a one-line italic caption.

## Architecture (as specified)

Read SPEC §2–§3 before writing any code; the key ideas that span many sections:

- **Pipeline** (§2.1): Parse (lossless, error-tolerant CST) → Evaluate (shared; only code that reads `variant` re-runs per variant) → then per variant and target: Style → Select → Sequence → Resolve → Step styling → Layout → Emit. The pipeline forks after Resolve and Step styling: PDF, live and preview go through Folio's own layout engine; DOCX and PPTX are generated from the resolved, step-styled tree (using Folio layout only for measurement).
- **Incremental and deterministic** (§2.3, §2.4): every stage is a memoised query built on `salsa` (early cutoff, cancellation, durability, cycle handling for the page-number fixpoint). Page breaking is strictly forward; the flow state is split into a *layout part* (decides breaks, must be `Eq` with a stable hash) and a *furniture part* (page numbers, running marks). The same inputs and the same compiler version must give byte-identical output: no wall-clock time; fonts and components pinned via `folio.lock`; `folio.toml` pins the language edition (syntax and semantics only) and the compiler version (output).
- **Crates** (§2.2): a workspace of `folio-*` crates (`syntax`, `eval`, `model`, `style`, `component`, `text`, `fonts`, `math`, `draw`, `layout`, `anim`, `runtime`, `edit`, `render`, `pdf`, `ooxml`, `preview`, `lsp`, `node`) plus the `folio` lib/bin exposing `folio::World` and `folio::compile(world, target, variant)`. This is the target structure; development starts with fewer crates and splits them out as interfaces settle, except the `folio-component` boundary, which is fixed from the start. `folio-syntax` starts as a fork of `typst-syntax` and `folio-math` from Typst's math layout (both Apache-2.0); PDF goes through `krilla`; `folio-render` and `folio-runtime` stay free of tokio and threads so they can compile to WebAssembly. Folio Studio (TypeScript/Electron, §12.4) lives in the same repo and uses `folio-node` (napi-rs).
- **Small core, components** (§3): anything not every document needs is a component that reaches the core only through the extension points in §3.2. First-party components (`folio-component-exam`, `-multicol`, `-plot`, `-timer`, `-inputs`) depend only on `folio-component`, never on core internals, and they are versioned with the compiler, not frozen per edition. The test for core vs component is in §3.1. Layout containers (§3.3) are the most demanding extension point and must support multicol as a component.
- **Source formats** (§4–§5): `.fol` content markup with a scripting layer, `.fsty` stylesheets (a CSS-like hybrid: expressions only in values and render templates; rationale in Appendix A; parsed losslessly like content, with one expression grammar shared by scripts, stylesheet values and templates), `folio.toml` manifest. Content says what things are; stylesheets say how they look. Local overrides are tracked; strict mode forbids them.
- **Variants** (§6): one source yields several outputs (exam, markscheme, slides); numbering groups share counters resolved on the common tree, and a leak check guarantees hidden content does not reach outputs.
- **Editor-first** (§1.4, §12.4): source positions, span maps, node identity and edit transactions exist from the first version so the visual editor is a front end, not a retrofit.

## Constraints

- `#![forbid(unsafe_code)]` everywhere except `folio-node` and font memory-mapping (§14.2). Those two declare their own `[lints]` table instead of inheriting the workspace one: `folio-fonts` copies the workspace lints with `unsafe_code = "deny"`, has `#![deny(unsafe_code)]` in its root, and allows unsafe code only in the `map` module of `src/cache.rs`. Keep its table in step with `[workspace.lints]`. The fuzz crate in `fuzz/` (a workspace of its own, never shipped) has neither the workspace lints nor the attribute: `fuzz_target!` exports a `no_mangle` function, which the lint rejects; its targets only call the safe harnesses in `folio-testkit`.
- Performance targets in §14.1 are release criteria (e.g. 5 ms for a typing edit's display list, warm full compile ≤ 400 ms p95); benchmark regressions are gated on instruction counts (Gungraun, formerly `iai-callgrind`; `scripts/bench.sh`), fail above 3%.
- Testing (§14.2): golden files for layout, normalised OOXML and animation steps; leak tests on every variant; the `folio-component` conformance suite for every component; fuzzing of parser and style matcher.
- Deterministic output (§2.4): no wall-clock time, no output that depends on hash-map iteration order or on how parallel work is scheduled, and no float operation whose result varies by platform. `clippy.toml` disallows `powi` and the `f32`/`f64` methods that call the system maths library (`sin`, `exp`, `powf`, `ln`, …); use the `libm` crate, or multiply out a small integer power.
- Component contracts (§3.5): pure, deterministic, memoisable, encapsulated, paint-only states, and total (a missing target mapping falls back, never fails a build).
